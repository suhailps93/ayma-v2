# Feature flags

Every runtime flag lives in ONE Firestore doc, `config/feature_flags`, read by
`functions/bootstrap/feature_flags.py` (typed, cached 60 s). This is the
`all-features-on` branch: every flag below defaults ON, i.e. the code defaults in
`config.py` are flipped. At last check (2026-10-25) the live `config/feature_flags` doc did not exist, so
the code defaults apply (plus any legacy `config/llm_routing` values). The architecture diagram and the
Inference-vs-Vertex routing table are in `docs/ARCHITECTURE.md` section 0.

## Resolution order (highest first)

1. `FLAG_<NAME>` environment variable (local dev, tests, emergency pin), e.g. `FLAG_MAPS_GROUNDING=false`.
2. `config/feature_flags` -> `<name>`.
3. Legacy docs, still honoured: `config/llm_routing` (`json|vision|chat|voice` groups, `fallback`) and `app_config/sentry` (`enabled`).
4. Code default in `config.py` (fed by the old per-flag env vars such as `LLM_ROUTE_JSON`).

A wrong-typed value is logged and ignored (next layer applies). An unreadable Firestore keeps the last good doc.

Separate from the Gemini transport switches above, the **vendor** switch is the per-surface `LLM_PROVIDER_<SURFACE>` env flags (hackathon Deliverable A, `config.py`, default `gemini` for every surface except `dm_coach` which defaults to `meta`, see below — not Firestore feature flags). `LLM_PROVIDER_VOICE=meta` routes the **Practice Date voice** session to the Meta cascade (Muse Spark LLM via the Meta Model API; STT + Inworld TTS + Silero VAD via the LiveKit Inference gateway — Meta serves no usable REST STT, so only the LLM leg is Meta; `agent.build_meta_cascade_session`), falling back to Gemini Live on a build failure **and** on a runtime cascade error (mid-call switch to a fresh Gemini Live session on the same room). Default voice behaviour is unchanged until flipped. STT/TTS vendor/voice/VAD are configurable via `META_CASCADE_STT_MODEL`/`META_CASCADE_TTS_MODEL`/`META_CASCADE_TTS_VOICE`/`META_CASCADE_VAD_MODEL`. Practice personas are **gender-matched**: `META_CASCADE_TTS_VOICE_FEMALE`/`META_CASCADE_TTS_VOICE_MALE` pick the Inworld voice by persona gender and **default to `Ashley` (feminine) / `Alex` (masculine)** so female personas sound female and male personas sound male out of the box (each falls back to `META_CASCADE_TTS_VOICE` only when explicitly blanked — before this they defaulted to empty, so every persona got the single vendor-default voice and gender was effectively ignored). Detail: `docs/META_PROVIDER.md` → "Voice cascade".

`LLM_PROVIDER_VOICE_MAIN=meta` does the same for the **MAIN (normal, non-practice) Ayma voice call** — a SEPARATE flag from `LLM_PROVIDER_VOICE` (which is Practice-only), so the two voices flip independently. Default `gemini`: the main call runs the LOCKED Gemini Live `RealtimeModel` exactly as today, zero behaviour change until the one env var is flipped. Unlike the other `LLM_PROVIDER_<SURFACE>` flags it does **not** inherit the global `LLM_PROVIDER` default — the main voice is the locked Gemini Live model, so a global `LLM_PROVIDER=meta` must never sweep it; only `LLM_PROVIDER_VOICE_MAIN=meta` can. When set to `meta` the main call is built as the same Meta cascade (`agent.build_meta_cascade_session`, reused from Practice) and **intentionally bypasses the locked Gemini Live voice** for Muse Spark. It keeps the normal call's behaviours (greeting/opener, barge-in, keepalive, idle watchdog, mute control, raw_turns memory flush, Sentry, app-driving tools) and meters voice tokens via `relay_cascade_usage` under `FEATURE_VOICE` with the same §F3 mid-call credit-cap stop. Same two fallbacks as Practice guarantee a flip can never take the main voice down: a build failure (no `META_API_KEY`, missing plugin) falls through to Gemini Live at start, and a mid-call cascade error switches to a fresh Gemini Live main session on the same room (reusing the one memory-flush window so persistence is never doubled). Caveat: mid-call voice/accent hot-swap (`set_voice_preference`) is Gemini Live-only; on the cascade it saves the preference for the next call instead of reconnecting. Flip: `LLM_PROVIDER_VOICE_MAIN=meta` on `ayma-agent` (via `scripts/deploy-agent.sh` `ENV`, `--release`). Detail: `docs/META_PROVIDER.md` → "Voice cascade".

`LLM_PROVIDER_DM_COACH` is the vendor switch for the **"Ayma in your DMs" assistant** (`dm_assist.py`, `POST /dm/assist` — opener chips on an empty thread + suggested next lines and a coaching tip on an active one, §6.9). Unlike every other surface it **defaults to `meta`** (Muse Spark via the Meta Model API) — a standing founder directive that the DM assistant runs on the Meta brain for the hackathon, so no env var is needed to get Meta here. It still inherits a global `LLM_PROVIDER` override and keeps the Gemini fallback (`LLM_META_FALLBACK`, default on), so a Meta hiccup degrades to Gemini and never blocks a thread; set `LLM_PROVIDER_DM_COACH=gemini` to pin it back to Gemini. Metered under the `icebreakers` token-ledger feature — spend is **recorded but not capped** (`enforce_cap=False`, like the Practice coach), so a zero-credit user still gets openers/coaching instead of a silently-empty bar (the credit cap otherwise raised `TokenCapExceeded` inside the assist and was returned as empty chips). Detail: `docs/META_PROVIDER.md` and `docs/ARCHITECTURE.md` §6.9.

`LLM_PROVIDER_TRANSLATE` is the vendor switch for **cross-language DM translation** (`dm_translate.py`, `POST /dm/translate` — translate an incoming message into the reader's language, or the reader's draft into the match's language, §6.12). Like `dm_coach` it **defaults to `meta`** (Muse Spark via the Meta Model API) — the cross-language dating feature is "powered by Muse" — so no env var is needed to get Meta here. It still inherits a global `LLM_PROVIDER` override and keeps the Gemini fallback (`LLM_META_FALLBACK`, default on); set `LLM_PROVIDER_TRANSLATE=gemini` to pin it to Gemini. Translation is a nicety that never blocks a thread (on any failure the client shows the original) and is metered under the `dm_translate` token-ledger feature, **cap-exempt** so a low-credit reader can still read what a match said. Detail: `docs/META_PROVIDER.md` and `docs/ARCHITECTURE.md` §6.12.

### Unified Brain — per-user LLM for all text surfaces (§13.10)

The per-surface `LLM_PROVIDER_*` flags above are superseded, **as the user-facing control**, by a single per-user **Brain**: one LLM vendor (`gemini` | `meta`) that drives **every text surface** — chat, matching, DM coaching, cross-language translation. It is chosen on the "Ayma's models" settings screen (Brain section, above Voice) via `GET`/`POST /brain/preference` and stored as `ayma_brain_model` on the user's profile. The `LLM_PROVIDER_*` env flags remain only as the **deploy-time default** used when a user hasn't picked a brain — so production/live behaviour is unchanged until a user chooses one.

**Capability-aware fallback (never a silently-dropped feature).** Each brain's capabilities are declared once in `llm_provider.BRAIN_CAPABILITIES`: **Gemini** has all five (`text`, `json`, `vision`, `web`, `tools`); **Meta/Muse Spark** has `text`, `json`, `tools` but **not** `vision` or `web`. A call states the capability it needs (`llm_provider.get_user_brain_provider(uid, surface, needs=…)`); if the chosen brain lacks it, the call resolves to **Gemini** instead. So with the Muse brain, chat/matching/DM/translation text runs on Muse, but **image reading and live web research always fall back to Gemini** — matching the in-code vision route (`get_vision_provider`, appearance reports) and the Gemini-only deep-dive/web research.

* `AYMA_BRAIN_DEFAULT` (default `meta`, i.e. **Muse Spark**) — the Brain shown pre-selected in the UI and used as the fallback brain when a user hasn't saved one. The hackathon runs on Muse by default (founder "default everything to Muse" rule); the capability fallbacks above keep web/vision on Gemini regardless. Selecting a brain picks a **vendor** only — the locked Gemini/Meta model ids (`config.py`) never change. Detail: `docs/ARCHITECTURE.md` §13.10, `docs/META_PROVIDER.md`.

### Per-user voice engine switcher (§13.9)

Beyond the deploy-time `LLM_PROVIDER_VOICE_MAIN` flag above, each user's voice **stack** is switchable per user from the user-facing "Ayma's models" settings screen (`/settings/voice`, reached from the normal Ayma settings menu — no longer developer-gated; it replaced the old Gemini-preset-only picker) via `GET /voice/engines` + `POST /voice/preference` (`voice_catalog.py`). `voice_mode=realtime|cascade` plus the chosen realtime model or brain/STT/TTS is stored on the user's profile and read by the agent at the next call (`main._voice_engine_seed` → room seed → `agent._run_session`); it overrides the deploy default for that user only, empty = the deploy default. The cascade dropdowns are populated **live** from the LiveKit Inference catalog (`GET /v1/models`, categorized by TYPE) when it is populated; config fallback (`VOICE_CASCADE_STT_MODELS`/`VOICE_CASCADE_TTS_MODELS`/`VOICE_CASCADE_LLM_MODELS`, `VOICE_CASCADE_EXTRA_BRAINS`) otherwise. **Today the fallback is the active path:** `GET /v1/models` returns an empty `{}` for this project (verified 2026-10-27 with an InferenceGrants JWT — the catalog simply is not populated for our plan), so the fallback lists enumerate the providers the project has LiveKit startup credits for, with canonical model ids from the LiveKit docs (`docs.livekit.io/agents/models`). On the fallback path availability is **honest**: a provider in `VOICE_CREDITED_PROVIDERS` is enabled; any other (e.g. `cartesia`) is shown **disabled** with a "needs LiveKit credits" note rather than a silently-failing pick (the live path, if populated, enables everything it returns). Every non-default path falls back to Gemini Live on error, so a voice-stack switch can never break a user's call.

New env, all read via `config.py`:

* `VOICE_OPENAI_REALTIME` (default `false`) — EXPOSES OpenAI Realtime as a selectable realtime model. It stays **inert** until both this flag is `true` **and** an `OPENAI_API_KEY` secret is mounted on `ayma-agent` (the founder must add that secret in Secret Manager; selecting OpenAI Realtime before then falls back to Gemini Live). `OPENAI_REALTIME_MODEL` (default `gpt-realtime`) sets the model id. Gemini Live needs no key.
* `VOICE_CASCADE_STT_MODELS` / `VOICE_CASCADE_TTS_MODELS` / `VOICE_CASCADE_LLM_MODELS` (CSV) — the **fallback** cascade component lists (the active path today, see above). Defaults: STT `deepgram/nova-3,assemblyai/universal-streaming`; TTS `inworld/inworld-tts-1,fishaudio/s2.1-pro,rime/coda,gradium/default,cartesia/sonic-3`; LLM `google/gemini-3.8-flash,google/gemini-3.7-flash,google/gemini-3.5-flash-lite`. All ids from the LiveKit docs.
* `VOICE_CREDITED_PROVIDERS` (CSV, lowercase; default `inworld,deepgram,fishaudio,assemblyai,rime,gradium,google`) — the provider segments the project has LiveKit Inference credits for. On the fallback path a cascade option whose provider is in this set is shown enabled; any other is shown disabled ("needs LiveKit credits"). Ignored when the live catalog is populated.
* `VOICE_CASCADE_EXTRA_BRAINS` (CSV of `id|route|model`) — extra cascade brains beyond the built-in Meta Muse + LiveKit LLMs.
* `VOICE_TTS_VOICES_<PROVIDER>` (CSV of `id` or `id|Label|gender`) — override a TTS provider's documented fallback voice list.
* `VOICE_ACCENT_CAPABLE_PROVIDERS` (CSV, lowercase; default `gemini,openai`) — provider segments whose voice honours the free-text **Accent** field (`ayma_voice_accent`, the "Ayma's models" accent box) at session boot. The instruction-driven native-audio realtime models (Gemini Live, OpenAI Realtime) take the accent in their instruction/style text; the fixed-voice cascade TTS providers are **not** listed and ignore it gracefully. One source of truth for `voice_catalog.provider_supports_accent` — the agent routes the accent only to capable providers (`agent._accent_block` → `prompts/voice_accent.md`), each catalog entry exposes `supports_accent`, and `set_voice_preference` tells the user to switch to an accent-capable model when the active one cannot change accent. Add a style-controllable TTS here once it genuinely honours an accent description. Detail: `docs/META_PROVIDER.md`, ARCHITECTURE §13.9.

Meta is **never** a realtime option (it serves no realtime audio API) — only a cascade brain. The LOCKED Gemini model ids are never edited; the selection only chooses provider/model/voice/language/accent.

## Flip, inspect, roll back

```
python3 scripts/flags.py list                              # effective value + source of every flag
python3 scripts/flags.py set maps_grounding=false --yes    # without --yes it is a dry run
python3 scripts/flags.py set llm_fallback_to_google=true llm_route_chat=vertex --yes
python3 scripts/flags.py rollback --yes                    # one line: restore the values from before the last write
python3 scripts/flags.py history
python3 scripts/flags.py load scripts/feature_flags.seed.json --yes   # first-time seed
```

Each write stores the previous flag values in the doc's `_history` (last 20), which `rollback` pops. `sentry` and `meta_integrations` are also mirrored to `app_config/<flag>.enabled`, because the mobile client reads those docs (it cannot read `config/feature_flags`). For `sentry` the app treats a missing doc as ON and only a literal `false` as off; `meta_integrations` is OFF unless the doc says a literal `true` (the app caches the last value for the next launch). Changes take effect within ~60 s, no deploy. The admin dashboard (`/admin`, "Feature flags") shows the effective values read-only (`GET /admin/feature-flags`).

## Requirements that come with these defaults

* Voice on Inference needs `livekit-agents` >= 1.8: `requirements-agent.txt` (the only agent image) pins 1.8.9 and `openai>=3.19,<4`. On the Google path 1.8.9 would default 3.8-live tools to NON_BLOCKING, so `agent.py` pins `tool_behavior=BLOCKING` (Developer API path only; Vertex rejects the field).
* The Meta voice cascade (`LLM_PROVIDER_VOICE=meta`) additionally needs `livekit-plugins-openai==1.8.9` (`requirements-agent.txt`) for its OpenAI-compatible Muse Spark LLM leg; STT, Inworld TTS and Silero VAD ride livekit-agents' built-in `inference` module, so no extra STT/TTS/VAD plugin. `META_API_KEY` and `LIVEKIT_API_KEY`/`SECRET` are already mounted on `ayma-agent`. The same `livekit-plugins-openai` also serves the voice-engine switcher's OpenAI Realtime option (§13.9) once `OPENAI_API_KEY` is added. The live catalog fetch (`GET /voice/engines`) uses the `LIVEKIT_API_KEY`/`SECRET` already on the Main API.
* Chat on Inference cannot ground on Google Search / Maps (the gateway has none): `web_search` runs as a function tool answered by a grounded Vertex call (unchanged). Maps grounding therefore only applies to chat turns that run on Vertex (Vertex route, or fallback).
* Models: only the locked ids are used (`config.py`): `google/gemini-3.7-flash` for JSON/vision/chat, `google/gemini-3.8-live` for voice. No new model id was introduced.

## Vertex AI Search (public websites)

* Resources (project `ayma-ai`, location `global`): data store `ayma-public-web` (`PUBLIC_WEBSITE`, 50 URI patterns from `scripts/vertex_search_domains.txt`) and Enterprise-tier engine `ayma-public-web-engine` (website search is not served by a bare data store). Recreate/sync with `python3 scripts/vertex_search_setup.py` (idempotent, uses your gcloud identity).
* Use: `vertex_search.py` queries the engine with the runtime identity (needs `roles/discoveryengine.viewer` or editor on the service account), parses profile URLs plus the already indexed `og:image`, and `deep_dive_public_profiles.py` merges them with the grounded Gemini results. No login, nothing third-party is fetched for indexed images, face verification is unchanged.
* Limits (basic website search): no domain verification is needed and none is possible for third-party domains. The store can only return pages Google has already crawled for those patterns; it cannot force a crawl, re-crawl or index login-walled content, and freshness is Google's. Advanced website indexing (on-demand recrawl, autocomplete, structured data) requires proving ownership of the domain and is not available for domains Ayma does not own.
* Cost: Enterprise-tier search is billed per query (list price about USD 4 per 1,000 queries; check the pricing page); the data store itself has no per-document charge for website search. The `vertex_ai_search_daily_cap` counter (`vertex_search_usage/{UTC date}` in Firestore) caps spend at 300 queries (about USD 1.20) per day by default. At the cap the source returns nothing and deep dives continue on the grounded source.

## The password-gated Developer panel

The hidden Developer panel is reached by 7 taps (or a long-press) on the version row at the bottom of User settings, from **any** account. Opening it shows **only a password field** — none of its contents (build / mode / account diagnostics, real-money spend, free reload, per-conversation cost, the dev test-upgrade row, the detailed release notes, the dev-only **Ayma's notes** entry) appear until the developer password is verified server-side. The unlock lives only in memory for the app session (`DevPanelSession`): a restart, or a long enough backgrounding (~5 min), re-locks it. The dev-only AI annotations (fact tags / confidence) render only inside the password-gated Ayma's-notes screen, never in the normal UI.

`POST /dev/test-upgrade` `{"plan": "plus"|"pro"|"max"}` (**`require_dev`-gated** — the dev-view allowlist `DEV_VIEW_UIDS` / `DEV_VIEW_EMAILS`, **403 for every other caller**) is a DEV/TEST-ONLY simulated upgrade with **no real payment**. It builds a synthetic entitlement for the chosen tier and runs it through the exact `billing.sync_entitlement` grant path a real RevenueCat purchase/entitlement uses, so it grants the genuine per-plan monthly pool (Plus 700 / Pro 1,400 / Max 8,000 credits) and sets the plan tier; it returns the refreshed `/usage` view plus `sync_status`. It exists so "credits depend on upgrade type" can be tested in a build where RevenueCat is off (`build-apk.sh --release` ships only the Test key, which native-kills in release). It is a free-credits cheat, so it is strictly dev-only — **never a revenue bypass for normal users** — and is surfaced in the app only on the Developer panel's **Test upgrade** row (Plus / Pro / Max), shown only when the panel is unlocked **and** the account is on the server's dev-view allowlist (`is_dev`). The real Upgrade button (disabled when subscriptions are unavailable) and the "fail loudly on bad RevenueCat key" guardrail are untouched.

`POST /dev/verify` `{"password": "..."}` (signed-in caller) performs the unlock check and changes nothing; it returns `{"ok": true}` on success. The app calls this when the password is entered. It checks the password server-side in constant time against the `DEV_PANEL_PASSWORD` secret (Secret Manager, mounted on `ayma-api` by `scripts/deploy-api.sh --full`); it never ships in the app and is never logged. Unset secret = refused (503). Lockout: 5 wrong passwords lock that account for 15 minutes and 10 from one client address lock that address for 15 minutes (counters in `dev_panel_attempts/{uid|ip_<hash>}`; the address is hashed); a generous global ceiling of 200 wrong passwords per 15-minute window (`_all`) stops a distributed run, and no few clients can reach it, so nobody is locked out by other people's guesses, plus a 10/minute rate limit on the endpoint.
