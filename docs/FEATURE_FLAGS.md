# Feature flags

Every runtime flag lives in ONE Firestore doc, `config/feature_flags`, read by
`functions/bootstrap/feature_flags.py` (typed, cached 60 s). This is the
`all-features-on` branch: every flag below defaults ON, i.e. the code defaults in
`config.py` are flipped. At last check (2026-10-25) the live `config/feature_flags` doc did not exist, so
the code defaults apply (plus any legacy `config/llm_routing` values). The architecture diagram and the
Inference-vs-Vertex routing table are in `docs/ARCHITECTURE.md` section 0.

## Resolution order (highest first)

0. **Per-uid demo override** (bool flags only): when `resolve(name, uid)` is called with a `uid` in `CONFIG.all_flags_on_uids`, every boolean flag resolves `True` (source `user_override`) — see "Per-uid all-flags-on override" below. Never touches the global doc.
1. `FLAG_<NAME>` environment variable (local dev, tests, emergency pin), e.g. `FLAG_MAPS_GROUNDING=false`.
2. `config/feature_flags` -> `<name>`.
3. Legacy docs, still read: `config/llm_routing` (`json|vision|chat|voice` groups, `fallback`) and `app_config/sentry` (`enabled`). Note: routing no longer honors `config/llm_routing` values since the 2026-11-04 direct-Google kill (everything is Inference-only) — the doc is retained for visibility only.
4. Code default in `config.py` (fed by the old per-flag env vars such as `LLM_ROUTE_JSON`).

A wrong-typed value is logged and ignored (next layer applies). An unreadable Firestore keeps the last good doc.

## Per-uid all-flags-on override (demo/judge accounts)

`feature_flags.resolve/get/enabled` take an optional `uid`. When that `uid` is in
`CONFIG.all_flags_on_uids` (env `ALL_FLAGS_ON_UIDS`, committed default = the three
demo uids `demo-test1,demo-test2,demo-test3`), **every boolean flag resolves ON**
for that user only, reported with source `user_override`. Non-bool flags (routes,
percents, lists, ints) have no meaningful "on" and are resolved normally. This is
a read-only short-circuit at the top of `resolve()`: it writes nothing and flips
no global flag, so no other account is affected.

Flags in `feature_flags.ALL_FLAGS_ON_DENYLIST` are **exempt** from this override
even though they are bools — currently `llm_fallback_to_google` (routing-audit
H11, kept as a guardrail although the flag is INERT since the 2026-11-04
direct-Google kill): it always resolves normally.

The override only applies where a call site passes a `uid`. User-facing gates with
a uid in hand (e.g. the deep-dive public-profiles gate) honour it; a few uid-less
gates (`sentry`, `vertex_ai_search`) and the two FastAPI-dependency gates whose
Instagram flow includes pre-login endpoints (`meta_integrations`, `mcp_server`)
remain globally governed by design. See `docs/DEMO_ACCOUNTS.md`.

### Unified Brain — per-user LLM for all text surfaces (§13.10)

The per-surface `LLM_PROVIDER_*` flags above are superseded, **as the user-facing control**, by a single per-user **Brain**: one LLM vendor (`gemini` | `meta`) that drives **every text surface** — chat, matching, DM coaching, cross-language translation. It is chosen on the "Ayma's models" settings screen (Brain section, above Voice) via `GET`/`POST /brain/preference` and stored as `ayma_brain_model` on the user's profile. The `LLM_PROVIDER_*` env flags remain only as the **deploy-time default** used when a user hasn't picked a brain — so production/live behaviour is unchanged until a user chooses one.

**Capability-aware fallback (never a silently-dropped feature).** Each brain's capabilities are declared once in `llm_provider.BRAIN_CAPABILITIES`: **Gemini** has all five (`text`, `json`, `vision`, `web`, `tools`); **Meta/Muse Spark** has `text`, `json`, `tools` but **not** `vision` or `web`. A call states the capability it needs (`llm_provider.get_user_brain_provider(uid, surface, needs=…)`); if the chosen brain lacks it, the call resolves to **Gemini** instead. So with the Muse brain, chat/matching/DM/translation text runs on Muse, but **image reading and live web research always fall back to Gemini** — matching the in-code vision route (`get_vision_provider`, appearance reports) and the Gemini-only deep-dive/web research.

* `AYMA_BRAIN_DEFAULT` (**QLOO-PHASE default `gemini`**) — the Brain shown pre-selected in the UI and used as the fallback brain when a user hasn't saved one. Qloo is judged before Meta, so new/unset users get Gemini (best-experience stack); **flips back to `meta` (Muse Spark) post-Qloo for the Meta hackathon**. The capability fallbacks above keep web/vision on Gemini regardless. Selecting a brain picks a **vendor** only — the locked Gemini/Meta model ids (`config.py`) never change. Detail: `docs/ARCHITECTURE.md` §13.10, `docs/META_PROVIDER.md`.

### Per-user voice engine switcher (§13.9)

Beyond the deploy-time `LLM_PROVIDER_VOICE_MAIN` flag above, each user's voice **stack** is switchable per user from the user-facing "Ayma's models" settings screen (`/settings/voice`, reached from the normal Ayma settings menu — no longer developer-gated; it replaced the old Gemini-preset-only picker) via `GET /voice/engines` + `POST /voice/preference` (`voice_catalog.py`). `voice_mode=realtime|cascade` plus the chosen realtime model or brain/STT/TTS is stored on the user's profile and read by the agent at the next call (`main._voice_engine_seed` → room seed → `agent._run_session`); it overrides the deploy default for that user only, empty = the deploy default. The cascade dropdowns are populated **live** from the LiveKit Inference catalog (`GET /v1/models`, categorized by TYPE) when it is populated; config fallback (`VOICE_CASCADE_STT_MODELS`/`VOICE_CASCADE_TTS_MODELS`/`VOICE_CASCADE_LLM_MODELS`, `VOICE_CASCADE_EXTRA_BRAINS`) otherwise. **Today the fallback is the active path:** `GET /v1/models` returns an empty `{}` for this project (verified 2026-10-27 with an InferenceGrants JWT — the catalog simply is not populated for our plan), so the fallback lists enumerate the providers the project has LiveKit startup credits for, with canonical model ids from the LiveKit docs (`docs.livekit.io/agents/models`). On the fallback path availability is **honest**: a provider in `VOICE_CREDITED_PROVIDERS` is enabled; any other is shown **disabled** with a "needs LiveKit credits" note rather than a silently-failing pick (the live path, if populated, enables everything it returns). `cartesia` is instead an enablement gate: its ids are withheld from the served lists until `CARTESIA_API_KEY` is wired, so an inactive Cartesia never appears in a selection list (founder ruling 2026-11-05). Every non-default path falls back to Gemini Live on error, so a voice-stack switch can never break a user's call.

New env, all read via `config.py`:

* `VOICE_OPENAI_REALTIME` (default `false`) — EXPOSES OpenAI Realtime as a selectable realtime model. It stays **inert** until both this flag is `true` **and** an `OPENAI_API_KEY` secret is mounted on `ayma-agent` (the founder must add that secret in Secret Manager; selecting OpenAI Realtime before then falls back to Gemini Live). `OPENAI_REALTIME_MODEL` (default `gpt-realtime`) sets the model id. Gemini Live needs no key.
* `VOICE_CASCADE_STT_MODELS` / `VOICE_CASCADE_TTS_MODELS` / `VOICE_CASCADE_LLM_MODELS` (CSV) — the **fallback** cascade component lists (the active path today, see above). Defaults: STT `deepgram/nova-3,assemblyai/universal-streaming,cartesia/ink-2,cartesia/ink-whisper`; TTS `inworld/inworld-tts-1,fishaudio/s2.1-pro,rime/coda,gradium/default,cartesia/sonic-3`; LLM `google/gemini-3.8-flash,google/gemini-3.7-flash,google/gemini-3.5-flash-lite`. All ids from the LiveKit docs.
* `VOICE_CREDITED_PROVIDERS` (CSV, lowercase; default `inworld,deepgram,fishaudio,assemblyai,rime,gradium,google`) — the provider segments the project has LiveKit Inference credits for. On the fallback path a cascade option whose provider is in this set is shown enabled; any other is shown disabled ("needs LiveKit credits") — except `cartesia`, which is hidden entirely until `CARTESIA_API_KEY` is wired. Ignored when the live catalog is populated.
* `VOICE_CASCADE_EXTRA_BRAINS` (CSV of `id|route|model`) — extra cascade brains beyond the built-in Meta Muse + LiveKit LLMs.
* `OPEN_WEIGHTS_BASE_URL` + `OPEN_WEIGHTS_MODEL` (+ optional `OPEN_WEIGHTS_API_KEY` secret) — the **self-hosted open-weights voice brain** (§13.9). When `OPEN_WEIGHTS_BASE_URL` is set, the cascade Brain (LLM) dropdown offers **"Llama 3.1 8B (open weights)"** (`open-weights-llama-3.1-8b`), routed via `livekit-plugins-openai` to that OpenAI-compatible endpoint (e.g. a Modal-hosted Llama) with model id `OPEN_WEIGHTS_MODEL` (`CONFIG.open_weights_model` — the agent throws rather than substitute a default if unset, so the call falls safely back to Gemini Live). **Opt-in only, never a default and never auto-selected**: prod leaves `OPEN_WEIGHTS_BASE_URL` unset, so the option is hidden and no production default changes (Gemini stays default everywhere; voice realtime stays Gemini Live). The same `OPEN_WEIGHTS_BASE_URL`/`OPEN_WEIGHTS_API_KEY` also back the TEXT `OpenWeightsProvider` (`LLM_PROVIDER_<SURFACE>=open-weights`), which uses `META_OPEN_WEIGHTS_MODEL` instead — the voice brain uses `OPEN_WEIGHTS_MODEL` because the voice endpoint may serve a different model. `ayma-agent` needs `livekit-plugins-openai` (already in `requirements-agent.txt`) for the LLM leg. Detail: ARCHITECTURE §13.9.
* `VOICE_TTS_VOICES_<PROVIDER>` (CSV of `id` or `id|Label|gender`) — override a TTS provider's documented fallback voice list.
* `INFERENCE_CHAT_MAX_TOKENS` (int, default `8192`) — the completion-token budget for a LiveKit Inference chat call (`config.inference_chat_max_tokens`, read in `gemini.py` — the only source; `gemini.py` carries no literal and throws if the config is unset). The chat model is a *thinking* model whose `completion_tokens` also counts reasoning, so the budget must leave room for visible content after the model reasons; the old `1024` burned the whole budget on reasoning against Ask-Ayma's ~17-18k-token prompt and returned empty content (→ `_CHAT_INCOMPLETE_REPLY`). On an empty response with `finish_reason == "length"`, chat retries once at 2× this budget before failing honestly — all on LiveKit, no provider reroute. Detail: ARCHITECTURE "Model routing", `docs/LIVEKIT_INFERENCE_MIGRATION.md`.
* `VOICE_ACCENT_CAPABLE_PROVIDERS` (CSV, lowercase; default `gemini,openai`) — provider segments whose voice honours the free-text **Accent** field (`ayma_voice_accent`, the "Ayma's models" accent box) at session boot. The instruction-driven native-audio realtime models (Gemini Live, OpenAI Realtime) take the accent in their instruction/style text; the fixed-voice cascade TTS providers are **not** listed and ignore it gracefully. One source of truth for `voice_catalog.provider_supports_accent` — the agent routes the accent only to capable providers (`agent._accent_block` → `prompts/voice_accent.md`), each catalog entry exposes `supports_accent`, and `set_voice_preference` tells the user to switch to an accent-capable model when the active one cannot change accent. Add a style-controllable TTS here once it genuinely honours an accent description. Detail: `docs/META_PROVIDER.md`, ARCHITECTURE §13.9.

Meta is **never** a realtime option (it serves no realtime audio API) — only a cascade brain. The LOCKED Gemini model ids are never edited; the selection only chooses provider/model/voice/language/accent.

### Per-user image model (image-gen restore, 2026-11-08)

The user picks which model Ayma uses to **generate and edit images in chat** from the same "Ayma's models" screen (`/settings/voice`), a dropdown independent of the Brain and the voice stack, via `GET /image-model/preference` + `POST /image-model/preference` (and folded into the Models-screen one-save `POST /models/preference` as `image_model`). The choice is stored on `users/{uid}/profile/main` as `ayma_image_model` and read by `image_gen.read_image_model_pref`; empty = the catalog default.

Image generation is the **ONE founder-authorized direct-Google inference exception**, scoped to image generation only (founder decision 2026-11-08). The direct Gemini image call lives solely in `functions/bootstrap/image_gen.py`, a **pluggable provider catalog**: entry 1 `gemini-direct` (the LOCKED `GEMINI_IMAGE_EDIT_MODEL`, the default and always available); entry 2 `xai-direct` (`grok-imagine-image-2.0`) ships **ready-but-unavailable** — with no `XAI_API_KEY` it is not listed and any routed call returns `unconfigured` with no provider call, becoming available with zero code change once the secret lands. Adding a model from any provider (including a future LiveKit image gateway) is adding one catalog entry. No silent fallback: a selection that can't be served returns a typed, honest outcome naming the vendor + model. Every OTHER inference path (chat, matching, JSON, vision, voice STT/TTS/realtime) stays LiveKit-only — the no-direct-Google static scan (`tests/test_llm_call_site_coverage.py`) exempts **only** `image_gen.py`.

New env, read via `config.py`:

* `IMAGE_GEN_DAILY_CAP` (int, default `100`) — hard daily cap on image-generation provider calls, enforced atomically in Firestore (`image_gen_usage/{YYYY-MM-DD}`, America/Los_Angeles day) in one `@firestore.transactional` BEFORE any provider call; **fail-closed** (a counter-store error → no provider call). `0` pauses image generation entirely. Same shape as `WEB_SEARCH_DAILY_CAP`.
* `XAI_API_KEY` (secret, default unset) — bearer key for the `xai-direct` entry. Until it exists the xAI model is not offered and never called; its absence is the shipped state.
* `IMAGE_GEN_XAI_MODEL` (default `grok-imagine-image-2.0`) — the `xai-direct` model id (the only image model id outside the Gemini family; same single-source rule).

No `app_registry.json` action entry (there is no `set_image_model` voice tool in this build): the picker is a control on the already-registered `/settings/voice` destination, whose aliases now include image-model phrasings so Ayma acknowledges and opens it.

## Flip, inspect, roll back

```
python3 scripts/flags.py list                              # effective value + source of every flag
python3 scripts/flags.py set qloo_enabled=false --yes      # without --yes it is a dry run
python3 scripts/flags.py set deepdive_validate_links=false --yes
python3 scripts/flags.py rollback --yes                    # one line: restore the values from before the last write
python3 scripts/flags.py history
python3 scripts/flags.py load scripts/feature_flags.seed.json --yes   # first-time seed
```

Each write stores the previous flag values in the doc's `_history` (last 20), which `rollback` pops. `sentry` and `meta_integrations` are also mirrored to `app_config/<flag>.enabled`, because the mobile client reads those docs (it cannot read `config/feature_flags`). For `sentry` the app treats a missing doc as ON and only a literal `false` as off; `meta_integrations` is OFF unless the doc says a literal `true` (the app caches the last value for the next launch). Changes take effect within ~60 s, no deploy. The admin dashboard (`/admin`, "Feature flags") shows the effective values read-only (`GET /admin/feature-flags`).

## Vertex AI Search (public websites)

* Resources (project `ayma-ai`, location `global`): data store `ayma-public-web` (`PUBLIC_WEBSITE`, 50 URI patterns from `scripts/vertex_search_domains.txt`) and Enterprise-tier engine `ayma-public-web-engine` (website search is not served by a bare data store). Recreate/sync with `python3 scripts/vertex_search_setup.py` (idempotent, uses your gcloud identity).
* Use: `vertex_search.py` queries the engine with the runtime identity (needs `roles/discoveryengine.viewer` or editor on the service account), parses profile URLs plus the already indexed `og:image`, and `deep_dive_public_profiles.py` merges them with the grounded Gemini results. No login, nothing third-party is fetched for indexed images, face verification is unchanged.
* Limits (basic website search): no domain verification is needed and none is possible for third-party domains. The store can only return pages Google has already crawled for those patterns; it cannot force a crawl, re-crawl or index login-walled content, and freshness is Google's. Advanced website indexing (on-demand recrawl, autocomplete, structured data) requires proving ownership of the domain and is not available for domains Ayma does not own.
* Cost: Enterprise-tier search is billed per query (list price about USD 4 per 1,000 queries; check the pricing page); the data store itself has no per-document charge for website search. The `vertex_ai_search_daily_cap` counter (`vertex_search_usage/{UTC date}` in Firestore) caps spend at 300 queries (about USD 1.20) per day by default. At the cap the source returns nothing and deep dives continue on the grounded source.

## The password-gated Developer panel

The hidden Developer panel is reached by 7 taps (or a long-press) on the version row at the bottom of User settings, from **any** account. Opening it shows **only a password field** — none of its contents (build / mode / account diagnostics, real-money spend, free reload, per-conversation cost, the dev test-upgrade row, the detailed release notes, the dev-only **Ayma's notes** entry) appear until the developer password is verified server-side. The unlock lives only in memory for the app session (`DevPanelSession`): a restart, or a long enough backgrounding (~5 min), re-locks it. The dev-only AI annotations (fact tags / confidence) render only inside the password-gated Ayma's-notes screen, never in the normal UI.

`POST /dev/test-upgrade` `{"plan": "plus"|"pro"|"max"}` (**`require_dev`-gated** — the dev-view allowlist `DEV_VIEW_UIDS` / `DEV_VIEW_EMAILS`, **403 for every other caller**) is a DEV/TEST-ONLY simulated upgrade with **no real payment**. It builds a synthetic entitlement for the chosen tier and runs it through the exact `billing.sync_entitlement` grant path a real RevenueCat purchase/entitlement uses, so it grants the genuine per-plan monthly pool (Plus 700 / Pro 1,400 / Max 8,000 credits) and sets the plan tier; it returns the refreshed `/usage` view plus `sync_status`. It exists so "credits depend on upgrade type" can be tested in a build where RevenueCat is off (`build-apk.sh --release` ships only the Test key, which native-kills in release). It is a free-credits cheat, so it is strictly dev-only — **never a revenue bypass for normal users** — and is surfaced in the app only on the Developer panel's **Test upgrade** row (Plus / Pro / Max), shown only when the panel is unlocked **and** the account is on the server's dev-view allowlist (`is_dev`). The real Upgrade button (disabled when subscriptions are unavailable) and the "fail loudly on bad RevenueCat key" guardrail are untouched.

`POST /dev/verify` `{"password": "..."}` (signed-in caller) performs the unlock check and changes nothing; it returns `{"ok": true}` on success. The app calls this when the password is entered. It checks the password server-side in constant time against the `DEV_PANEL_PASSWORD` secret (Secret Manager, mounted on `ayma-api` by `scripts/deploy-api.sh --full`); it never ships in the app and is never logged. Unset secret = refused (503). Lockout: 5 wrong passwords lock that account for 15 minutes and 10 from one client address lock that address for 15 minutes (counters in `dev_panel_attempts/{uid|ip_<hash>}`; the address is hashed); a generous global ceiling of 200 wrong passwords per 15-minute window (`_all`) stops a distributed run, and no few clients can reach it, so nobody is locked out by other people's guesses, plus a 10/minute rate limit on the endpoint.
